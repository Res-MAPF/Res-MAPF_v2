# src/view

The GUI layer, built on `customtkinter`. It lets a user build or load a MAPF instance, solve it (or batch-solve a saved test set), and then step through — or interactively inject failures into — the resulting resilient plan. None of the solving logic lives here; these modules build the window, wire up widget behavior, and call into [domain/solver/](../domain/solver/README.md) and [utils/](../utils/README.md).

## Files

| Module | Description |
|--------|-------------|
| `state.py` | `AppState` — the shared object holding every Tk variable/widget reference |
| `layout_builder.py` | Builds the main window's entire widget tree |
| `handlers.py` | Wires up what each button in the main window actually does |
| `console_redirector.py` | Redirects `stdout`/`stderr` into the GUI's console textbox |
| `controller.py` | `MainGUIController` — top-level object that assembles and runs the app |
| `grid_visualizer.py` | The plan playback / interactive failure-simulation window |

### `state.py`
`AppState(root)` is a plain holder for everything the main window's widgets are bound to: `agent_list` (the in-progress instance's start/goal pairs), the map/`k`/`h`/`m` string variables, the instance-generation form's variables, and `fail_type_vars` (one `BooleanVar` per failure type checkbox: `topw`, `tops`, `individual`, `high-level`). One instance is created by `MainGUIController` and passed through `build_layout()`/`configure_handlers()` so the two stay in sync without module-level globals; `layout_builder.py` also attaches widget references directly onto this same object (e.g. `state.solve_button`) as it builds them.

### `layout_builder.py`
`build_layout(root, state)` constructs the entire main window: the "Create instance" panel (start/goal coordinate entry, add/remove-agent list, map/k/m/h fields, failure-type checkboxes, save-instance button), the "Load instance from file" and "Load and simulate plan" panels, the "Generate test instances" panel, the console output textbox, and the bottom Solve/Run Test/Kill Terminal button row. It creates every interactive widget and stores a reference to it on `state` (e.g. `state.map_var`, `state.solve_button`, `state.agent_listbox`) but does not attach any button commands itself, except for `run_test_button` and `kill_button`, which it wires directly to `handlers.handle_run_test`/`handle_kill_terminal`. Returns the console `CTkTextbox`. This is the file to change for the main window's visual layout.

### `handlers.py`
`configure_handlers(root, state, console_textbox)` attaches the actual command callbacks to every other button `layout_builder` created: `add_agent`/`remove_agent` (maintain `state.agent_list`), `handle_save_instance`/`handle_load_instance` (via `plan_io.save_instance_to_file`/`load_instance_from_file`), `handle_simulate_plan` (loads a saved plan pickle and opens a `GridVisualizer`), `handle_generate_instances` (calls `domain.generation.generate_test_instances`), `handle_solve`, and `copy_console`/`clear_console`. `handle_solve()` is the main "Solve k-R MAPF" action: it reads the form fields into a `MAPFInstance`/`RobustnessParams`/empty `SearchParams`, runs `solve_mapf_with_profiling()` on a background thread guarded by a `TIME_LIMIT` (3600s) timeout-watcher thread, and on success saves the solution pickle, logs a CSV row via `sperimental_analysis.build_solutions_csv`, and opens a `GridVisualizer` window. `handle_run_test(root, state)` (called by `layout_builder` for the "Run Test" button) opens a separate dialog to pick a saved `data/test_instances/*.pkl` set plus k/m/h/failure types and an optional "Granular Profiling" mode, then batch-solves every instance in it on a background thread (`_run_test_in_thread`), optionally writing a full markdown profiling report per instance via `profiling.generate_profiling_markdown`/`save_profiling_report`. `handle_kill_terminal()` restores stdout/stderr and relaunches the whole GUI as a fresh subprocess (`python -m src.main`) — the escape hatch for a stuck/runaway solve. This is the file to change for what a button actually does.

### `console_redirector.py`
`ThreadSafeConsoleRedirector(textbox, root)` replaces `sys.stdout`/`sys.stderr` so that `print()` calls made from background solver threads end up in the GUI's console textbox instead of (or in addition to, if not yet ready) a real terminal. Writes are marshaled onto the Tk main thread via `root.after(0, ...)` under a lock, and messages are buffered if the textbox doesn't exist yet or has been destroyed; `restore()` puts the original streams back. Installed and torn down by `controller.py`.

### `controller.py`
`MainGUIController` is the GUI's top-level object, instantiated once by `src/main.py`. Its constructor builds the root `CTk` window and `AppState`, calls `layout_builder.build_layout()` then `handlers.configure_handlers()`, and installs the `ThreadSafeConsoleRedirector` (with a short retry via `root.after(100, ...)` if the console textbox isn't ready immediately). `on_closing()` restores stdout/stderr before destroying the window (bound to the window's close protocol), and `run()` starts `root.mainloop()`, restoring the console redirector in a `finally` block afterward.

### `grid_visualizer.py`
`GridVisualizer(root, grid, mapf_instance, robustness_params, solution)` is the plan-playback and failure-simulation window opened after a successful solve or when loading a saved plan. It draws the map on a zoomable/pannable `CTkCanvas` (mouse-drag panning, zoom in/out buttons) with start/goal cell markers, per-agent colored dots at the current step, and an optional "Show Full Paths" trail overlay; `next_step`/`previous_step`/`play_all` step through the plan (`extract_nominal_paths()` replays the macro-action plan into a per-agent position list via the module-level `apply_action()` helper). The right-hand panel lets the user pick an agent and a failure type (restricted to whichever types are in `robustness_params.selected_failure_types`) and click "Simulate failure": `apply_selected_agent_failure()` computes which actions become newly forbidden via `resplan_solver.compute_affected_actions()`, decrements the remaining `k` budget and that agent's `h` count (bailing out if either is exceeded), and re-invokes `solve_mapf()` with a `SearchParams` seeded from the *previous* solve's `R_up`/`R_down`/`predecessors` so the search can resume rather than restart — splicing the new resilient continuation onto the plan prefix already executed. A running failure log and per-agent path listing are kept in side textboxes (`update_failure_log()`/`update_paths_display()`). This is the largest and most stateful module in `view/` — the file to change for anything about how a solved plan is displayed or how the interactive failure-injection demo behaves.
